# Personal AI Workbench 源码走读指南

> 配套文档：`docs/项目架构与开发流程.md`（整体框架）
> 目的：给出一条从“跑起来”到“读懂每个子系统”的递进走读顺序，每阶段都给出文件清单、入口锚点和自检问题。

## 0. 走读总原则

- **先跑起来，再读代码**：先 `cd Workbench && npm install && npm run dev`，边看代码边对照页面效果。
- **跳过产物目录**：`Workbench/node_modules/`、`Workbench/dist/`、`release/`、`build/*.log` 不读；
  `Workbench/server/server-bundle.mjs` 是 esbuild 打包产物（超 1MB），只读 `standalone.mjs` 入口即可。
- **以“一条主线”串联**：不要按字母顺序读文件，先选一条端到端链路（见第 10 节），把它读透再展开。
- **对照测试读**：每个子系统都有对应 `Workbench/tests/*.test.mjs`，测试即文档，能快速确认模块职责。

## 1. Phase 0 · 规则与总览（约 30 分钟）

先建立“哪些能做、哪些不能做”的边界感，后面读代码时才能理解很多设计取舍。

| 文件 | 读什么 |
|---|---|
| `AGENTS.md`（根目录） | 公开数据边界、功能边界、三道发布门禁 |
| `README.md`（根目录） | 项目定位、能做什么、目录结构 |
| `Workbench/README.md` | Workbench 快速开始、Vault 结构建议、隐私边界 |
| `Workbench/docs/public-release-boundaries.md` | 可复用/不可转移边界、模块公开状态表、发布清单 |
| `docs/项目架构与开发流程.md` | 整体架构速览（本指南的上级文档） |

**自检**：能说出 Brainstorm / 90_runs / 微信公众号为何不公开，以及 demo 数据必须满足什么条件。

## 2. Phase 1 · 启动与构建链路（约 1 小时）

目标：理解“一个命令 `npm run dev` 之后发生了什么”，以及“安装包是怎么打包出来的”。

推荐顺序：

1. 根目录 `package.json` —— Electron 壳的 scripts（`dev` = `electron .`，`dist` = electron-builder NSIS）。
2. `electron/main.js` —— 壳的主进程：
   - 单实例锁、用户数据目录迁移；
   - 开发模式：spawn `vite`；生产模式：spawn `server-bundle.cjs --port 5173`；
   - 首次启动从 `seed.tar.gz` 解压运行环境（`ensureRuntimeAsync` / `checkNeedExtract`）。
3. `Workbench/package.json` —— 核心项目的 scripts（dev/test/build/privacy:scan/demo:generate）。
4. `Workbench/vite.config.mjs` —— Vite 配置，注意 `workbenchApiPlugin()` 和 `host: 127.0.0.1`。
5. `Workbench/server/standalone.mjs` —— 生产入口：
   - 用一个 fake Vite server 捕获插件注册的 API handler；
   - 裸 `node:http` 托管 `dist/client` + SPA fallback，端口 5173。
6. 根目录 `scripts/build-production.ps1` + `scripts/prepare-seed.ps1` —— 桌面发布链路（vite build → esbuild 单文件 → seed.tar.gz）。

**自检**：开发/生产两条启动路径分别启动什么进程？为什么生产版运行期不需要 node_modules？

## 3. Phase 2 · 后端数据层与 API（约 2–3 小时）

这是全项目的心脏，建议按依赖顺序读，即“安全 → 索引 → 同步 → 路由 → 领域载荷”。

推荐顺序：

1. `Workbench/server/security.mjs` —— 先理解约束：
   - `validateVaultSelections`（路径白名单、相对路径校验、大小限制）；
   - `DEFAULT_ALLOWED_ROOTS`、`writeConfirmedDraft`。
2. `Workbench/server/vault-index.mjs` —— 索引层：
   - `buildVaultIndex`（目录扫描、frontmatter 解析、隐私路径跳过、全文索引）；
   - `searchIndex`、`getDocument`、`attachPublishedWorkArchives`；
   - 注意 `PUBLIC_HIDDEN_PATH_PREFIXES`（Brainstorm/90_runs/public-account）。
3. `Workbench/server/vault-sync.mjs` —— 实时性：
   - 文件监听、去抖、临时文件过滤；
   - `affectedScopesForPaths`（路径 → 失效 scope 映射）；
   - SSE 事件格式（`vault.index.changed`）。
4. `Workbench/server/vite-plugin-workbench.mjs` —— **API 路由中心，全文最重要的一个文件**：
   - 从 `workbenchApiPlugin().configureServer` 开始读；
   - 按顺序扫一遍 `/api/*` 分支：overview / collections / search / documents / reader-notes / reader-explanations / graph / douyin / social-insights / refresh / runtime / open / workflows / wiki-ingest / vault sync & events；
   - 对照 `Workbench/src/lib/api.js` 的导出函数看前端怎么调。
5. 领域载荷模块（每个都很短，读 export 函数即可）：
   - `materials.mjs`、`books.mjs`（素材/书架）；
   - `social-insights.mjs`（Markdown 报告解析，注意 REQUIRED_SECTIONS）；
   - `material-reading-state.mjs`、`reader-notes.mjs`、`reader-explanations.mjs`（阅读状态/笔记/解释服务）；
   - `public-config.mjs`（attention 策略加载：local 覆盖 default）。

**自检**：`GET /api/documents/:id` 从请求到响应经过了哪几个模块？一个 Vault 文件变化后，前端哪些页面会刷新？

## 4. Phase 3 · 前端骨架与 API 客户端（约 1 小时）

目标：理解 SPA 如何组织、如何与后端通信、失败时如何降级。

推荐顺序：

1. `Workbench/src/main.jsx` —— 入口（createRoot + BrowserRouter + 字体）。
2. `Workbench/src/App.jsx` —— 路由表 + 全局状态：
   - `localWorkbench = VITE_WORKBENCH_HOSTED !== "true"` 决定社媒洞察等页面是否渲染；
   - `useVaultSync` 驱动的 `routeRevision`（Vault 变化自动重挂路由刷新页面）。
3. `Workbench/src/components/AppShell.jsx` —— 导航与布局（对照路由表）。
4. `Workbench/src/lib/api.js` + `Workbench/src/lib/api-errors.js` —— 统一请求封装：
   - `withFallback`（live → fallback 降级）；
   - 超时/错误归一化。
5. `Workbench/src/data/fallback.js` —— 降级数据语义：缺失保持 `null`/空数组，绝不虚构为 `0`。
6. `Workbench/src/hooks/useVaultSync.js` —— EventSource 消费 SSE，按 scope 递增 revision。

**自检**：托管版（`VITE_WORKBENCH_HOSTED=true`）和本地版在页面与 API 上有什么差异？

## 5. Phase 4 · 页面层（约 2–3 小时）

按“简单 → 复杂”顺序读，每个页面基本是同一套路：页面组件 → 调 `lib/api` → 渲染组件。

推荐顺序：

1. `pages/SystemPage.jsx` —— 最薄，只读 runtime 状态，适合热身。
2. `pages/OverviewPage.jsx` —— 总览：overview + graph 双数据源、GSAP 入场动画。
3. `pages/CollectionPage.jsx` —— 通用集合列表（/wiki、/content 共用），理解 `kind` 参数。
4. `pages/MaterialsPage.jsx`、`pages/BooksPage.jsx` —— 素材层与书架，配合 `components/materials/*`。
5. `pages/DailyHotPage.jsx` —— 每日热点，配合 `shared/ai-hot.mjs`（前后端共享模块的范例）。
6. `pages/DouyinPage.jsx` + `components/douyin/DouyinDashboard.jsx` —— 抖音面板，注意“缺数据保持缺失”。
7. `pages/SocialInsightsPage.jsx` + `components/social-insights/*` —— 社媒洞察展示（仅本地版）。
8. `pages/GraphPage.jsx` —— 星图页面（引擎本身放 Phase 5 单独读）。

**自检**：任意选一个页面，能画出“组件 → API 函数 → 后端路由 → 数据来源”的调用链。

## 6. Phase 5 · 知识星图引擎（独立子系统，约 2–3 小时）

`src/graph/` 是一套脱离 React 的 Canvas 场景引擎，值得单独读。React 组件只是薄壳。

推荐顺序（从数据到渲染）：

1. `src/lib/graph.js` —— 常量：节点半径、类型/状态颜色与标签（先知道“画什么”）。
2. `src/graph/graph-model.js` —— 数据模型（节点/边归一化、邻居索引）。
3. `src/graph/graph-layout.js` —— 布局（computeBaseLayout + d3-force 力导向 + 视口适配）。
4. `src/graph/graph-motion.js` —— 动画状态机（阻尼、hover/选中目标、reduced-motion）。
5. `src/graph/graph-renderer.js` —— Canvas 绘制（节点/边/标签/辉光）。
6. `src/graph/graph-hit-test.js` —— 命中测试与 hover 意图。
7. `src/graph/graph-engine.js` —— **主循环**，把所有模块拼成单一 Canvas clock。
8. `src/hooks/useKnowledgeGraphEngine.js` + `src/components/KnowledgeGraph.jsx` —— React 接入层。

**自检**：选中一个节点后，动画、命中测试、标签缓存、相机分别由哪个模块负责？

## 7. Phase 6 · 阅读器与笔记（最复杂的交互链路，约 2–3 小时）

阅读器跨前端组件、前端纯函数、后端服务、共享契约四层，建议按“入口 → 渲染 → 状态 → 后端”读。

推荐顺序：

1. `src/components/DocumentDrawer.jsx` —— 抽屉入口（打开文档、阅读队列、加载文档）。
2. `src/components/reader/ReaderWorkspace.jsx` —— 阅读工作区（Markdown 渲染、笔记面板、解释面板）。
3. 前端纯函数（先读，理解“文本如何变成可交互结构”）：
   - `src/lib/reader-markdown.js`（Markdown → 结构化块）；
   - `src/lib/reader-anchors.js`（锚点/定位）；
   - `src/lib/reader-ui.js`（UI 状态）；
   - `src/lib/reader-explanation-thread.js`（解释对话线程）。
4. 共享契约：`shared/reader-text-contract.mjs` —— 前后端必须一致的文本块/锚点契约。
5. 后端服务：
   - `server/reader-notes.mjs`（笔记持久化：hash 内容 → 快照 → 仓库）；
   - `server/reader-explanations.mjs`（AI 解释服务：prompt、结果 schema 校验、状态机）。

**自检**：阅读笔记存到哪里？如何保证笔记和原文版本对应（内容 hash 的作用）？

## 8. Phase 7 · AI 集成（Codex 任务，约 1–2 小时）

项目通过 Codex CLI 子进程执行 AI 任务，包含一个任务状态机。

推荐顺序：

1. `server/codex-runner.mjs` —— 通用任务执行器：
   - `CODEX_EXEC_ARGS`（`--json --sandbox read-only --ephemeral`，安全参数）；
   - 状态机 `JOB_STATUS`（queued → running → awaiting_review → completed/failed/cancelled）；
   - 小红书图文草稿工作流（`createXhsDraftJob`）与桌面回退。
2. `server/wiki-ingest-runner.mjs` —— 更完整的流水线：
   - `WIKI_INGEST_STATUS`（plan → review → revise → confirm → execute）；
   - 两个 sandbox 级别（只读规划 / workspace-write 执行）；
   - 客户端交接包（`createWikiIngestClientHandoff`）。
3. 前端：`pages/WorkflowPage.jsx` + `src/lib/api.js` 中 `startWorkflow / loadWorkflowJob / createJobEventSource`。

> 注意：`WorkflowPage` 当前**没有挂进 `App.jsx` 路由**（代码已实现、入口未接），走读时注意区分“已接线”和“未接线”功能。

**自检**：为什么规划阶段用 `read-only` 沙箱、执行阶段才用 `workspace-write`？草稿写入需要什么确认？

## 9. Phase 8 · 托管、发布与隐私门禁（约 1 小时）

1. `Workbench/worker/index.js` —— Cloudflare Worker：托管构建的 SPA 回退（404 → index.html）。
2. `Workbench/scripts/prepare-sites-build.mjs` —— 组装 Sites 产物（dist/client + worker + hosting.json）。
3. `Workbench/scripts/privacy-scan.mjs` —— 发布门禁：正则检查家目录路径/凭据/私钥/私有标识。
4. `Workbench/scripts/generate-demo-douyin.mjs` —— 确定性生成抖音演示数据。
5. `Workbench/templates/douyin/README.md` + `current.template.json` —— 抖音数据契约门槛。
6. `Workbench/config/attention.default.json` + `.example.json` —— 策略配置与本地覆盖。

**自检**：privacy:scan 排除了哪些目录？为什么 `Workbench/scripts/privacy-scan.mjs` 自身被排除？

## 10. 推荐的三条端到端主线（任选其一跑通，再展开其他）

### 主线 A · 一篇 Wiki 页面从 Vault 到屏幕（推荐第一遍走）

```
个人知识库/wiki/concepts/xxx.md
  → server/vault-index.mjs buildVaultIndex（frontmatter + 全文索引）
  → server/vite-plugin-workbench.mjs GET /api/collections/wiki
  → src/lib/api.js loadCollection
  → src/pages/CollectionPage.jsx 渲染列表
  → 点击 → DocumentDrawer → GET /api/documents/:id → 阅读器渲染
```

### 主线 B · 知识星图

```
server/vault-index.mjs（graph 载荷）→ GET /api/graph
  → src/pages/GraphPage.jsx / OverviewPage
  → components/KnowledgeGraph.jsx → hooks/useKnowledgeGraphEngine
  → graph/graph-engine.js 主循环（model → layout → motion → renderer → hit-test）
```

### 主线 C · Vault 变化实时刷新

```
文件系统变化 → server/vault-sync.mjs（监听 + 去抖 + scope 映射）
  → SSE /api/vault/events → src/hooks/useVaultSync.js（revision +1）
  → App.jsx routeRevision 变化 → 受影响页面重挂重取
```

## 11. 文件定位速查（一句定位） 

| 文件 | 一句话定位 |
|---|---|
| `server/vite-plugin-workbench.mjs` | API 路由中心，所有后端能力的总入口 |

| `src/lib/api.js` | 前端 API 客户端 + fallback 降级 |
| `src/graph/graph-engine.js` | 星图引擎主循环 |
| `src/components/reader/ReaderWorkspace.jsx` | 阅读器工作区 |
| `server/codex-runner.mjs` | Codex CLI 任务状态机 |
| `server/wiki-ingest-runner.mjs` | Wiki 导入流水线 |
| `shared/ai-hot.mjs` | 每日热点共享逻辑（前后端复用范例） |
| `shared/reader-text-contract.mjs` | 阅读器前后端契约 |
| `scripts/privacy-scan.mjs` | 发布隐私门禁 |
| `electron/main.js` | 桌面壳：拉起服务、加载窗口 |

## 12. 走读节奏建议

- 第一遍（半天）：Phase 0–3 + 主线 A，建立“请求-响应”心智模型。
- 第二遍（1–2 天）：Phase 4–6，逐页读组件，配合浏览器 DevTools 看 API 返回。
- 第三遍（按需）：Phase 7–8 + 测试，深入 AI 任务、发布流程和边界设计。
- 每读完一个模块，用 `node --test tests/<对应测试>.test.mjs` 跑一遍对应测试，验证理解。
